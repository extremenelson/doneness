## Problem Statement

Running several coding agents in parallel on one repo breaks down in predictable ways: agents claim "done" while checks fail, they collide on shared resources (several full test suites at once, git lock contention), and nothing tells a human which branch is actually proven. Today `newproj` solves this only for brand-new Go repos it scaffolds itself, in the author's personal layout. The goal is for other people to get the same guarantees on repos they already have.

## What Makes This Cool

One command on a repo you don't own (`newproj adopt`) and, afterwards, parallel Claude Code agents in it **can't accidentally claim done and can't overload the machine** (other agents get the advisory rules block only; the Stop hook is Claude Code's). The gate is derived from the repo's own build files, enforced by the agent's stop hook, verify-only, fail-closed, and every pass leaves a receipt tied to the exact tree hash, so an unchanged tree is a free cache hit.

**What the guarantee covers.** It protects against mistaken or careless done-claims, which is the common failure: an agent that stops early, skips the tests, or reports success over a red run. It doesn't protect against an adversarial agent with a shell, which could edit `.newproj.json`, remove the hook, or write a fake note. v1 makes that kind of tampering *visible* rather than impossible: receipts carry a hash of the gate config, and `gate --status` flags config drift from the base branch and a missing hook entry. Receipts are advisory until they're verified off-machine (Approach B).

## Constraints

- Audience is other developers (open source), not just the author: no personal defaults hardcoded (today `defaultPrefix = "github.com/extremenelson"`, `main.go:28`).
- Must be safe on first contact with someone else's repo: never moves the repo by default, dry run by default.
- Must not require beads (`bd`); light up bd features only when bd is on PATH.
- Must work alongside existing worktree tools (gtr, agent-worktree, plain `git worktree`).
- macOS and Linux for v1; Windows deferred (locking uses flock).

## Premises

1. The product is an enforced definition of done, not boilerplate: one check command wired into the stop hook, CI and agent rules; `adopt` reports "ready" only after it runs green once.
2. Retrofit first and safe on first run: in place by default (worktrees in `<repo>.wt/`), dry run by default, `--container` opt-in.
3. *(Revised after second opinion)* `newproj gate` is the product and is callable by any worktree tool. `newproj wt` is a thin optional convenience, not v1 core.
4. Distribution is one Go binary: bash helpers become subcommands over time; personal defaults are derived from git config/remote.
5. Gates verify, never rewrite: the enforced command is read-only; fixers (`fmt`, `tidy`) live in a separate target.

## Recommended Approach

**Approach A.** It's the fastest path to the demo: adopt a repo you don't own, then show that four agents can't accidentally claim done.

### `newproj gate`

```
newproj gate [--hook] [--budget DURATION] [--no-cache]
newproj gate --status [<rev>]
```

1. **Resolve the command** from `.newproj.json` at the repo root (`{"gate":{"command":"..."}}`, owned by `internal/gate` per D6). No config, an empty command, or a command not found → **exit 2** with a message naming `newproj adopt`. Never exit 0 without running something. `config_hash` = sha256 of the canonical re-marshal of the `gate` object. In hook mode the repo is `git -C <stdin cwd> rev-parse --show-toplevel` (D7).
2. **Tree hash**, used twice. Copy the real index (path from `git rev-parse --path-format=absolute --git-path index`, which is correct in linked worktrees where `.git` is a file) to a temp file. Run `GIT_INDEX_FILE=<tmp> git add -A && git write-tree`. Seeding from the real index keeps tracked-but-ignored files in the hash and reuses git's stat cache, so unchanged files aren't rehashed. The real index is untouched.
3. **Cache check (pre-lock hash):** if `refs/notes/newproj-gate` has a PASS receipt on that tree with the same command, `config_hash`, `newproj_version` and GOOS/GOARCH (D10, D18), print `gate: cached pass (<tree> <age>)` and exit 0. `--no-cache` skips this.
4. **Lock:** take one of N flock slots under `${XDG_STATE_HOME:-~/.local/state}/newproj/locks/`. **N is machine-level only:** `NEWPROJ_SLOTS`, else `slots` in `${XDG_CONFIG_HOME:-~/.config}/newproj/config.json`, else max(1, CPUs/4). Repos can't set it, so the cap holds across every repo and worktree. Print `gate: waiting for slot` while blocked. The slot wait counts against `--budget` (step 9).
5. **Baseline hash:** recompute the tree hash *after* the slot is acquired. The receipt is keyed to this tree, the one actually tested.
6. **Run** `sh -c <command>` in the repo toplevel, in its own process group, with `CI=1` (unless set) and stdin=/dev/null; output streamed (non-hook mode) or captured (hook mode). The slot's locked fd is inherited by the check so the slot stays held until the whole group exits, even if gate is SIGKILLed (Linux also sets Pdeathsig). On deadline or SIGINT/SIGTERM, SIGTERM the group, SIGKILL after 5s (D5, D8, D13, D16).
7. **Mutation guard:** recompute the tree hash and compare it to the step 5 baseline. If it changed, **fail** with `gate: tree changed during the check (the command wrote files, or something edited the tree concurrently); the gate must be verify-only`, plus the changed paths. **Release the slot here**, after the guard and before the receipt write.
8. **Receipt (PASS only, D14):** on pass, write `git notes --ref=newproj-gate add -f -m '<json>' <tree>` with `{tree, command, config_hash, duration_ms, at, host, goos, goarch, newproj_version}`, keyed to the step 5 baseline tree. Failures (command failure, guard, timeout) write no note; the last red outcome per tree goes to `${XDG_STATE_HOME:-~/.local/state}/newproj/last/<tree>`. Worktrees share the notes ref, so on `cannot lock ref` the write retries five times with backoff (50ms doubling to 800ms); if it still fails, gate passes with the warning `gate: PASS, but receipt not recorded (<err>)` (a `systemMessage` in hook mode). Exit codes outside hook mode: 0 pass/cached, 1 check failed, 2 config error (shell exit 127 reported as "command not found" on a best-effort basis), 3 tree changed, 4 timeout (D8).
9. **`--hook` mode** (Claude Code Stop hook):
   - **Output channels.** gate --hook **always exits 0 and writes one JSON object to stdout**. A Stop hook can block on exit 0 with `{"decision":"block","reason":...}`, and only on exit 0 does Claude Code read stdout JSON. To **block**: `{"decision":"block","reason":"<last 60 lines of output>"}`, where the reason goes to the agent. To **allow**: `{}`. **Anything a human must see**, on either path (the receipt-write warning from step 8, NOT DONE, timeouts), goes in a `systemMessage` field on the same object, which Claude Code shows to the user. So a blocking attempt can carry a user-visible warning too. The only non-JSON exit is a crash of the binary itself, which Claude Code reports as a non-blocking hook error.
   - **Loop guard.** `stop_hook_active` no longer short-circuits: the gate runs on every stop attempt, and an unchanged green tree is a cache hit. Runaway loops are bounded by a per-session counter at `${XDG_STATE_HOME:-~/.local/state}/newproj/sessions/<session_id>`. **Every blocking outcome increments it**, including the step 1 config errors (no `.newproj.json`, empty command, command not found), command failure, mutation-guard failure, budget timeout, and a timeout in the slot wait. **The counter counts consecutive blocked stops in the session and does not depend on the tree**, so a check that rewrites files on every run, or a worktree missing its config, still reaches the limit. Attempts 1-2: block. Attempt 3, matching the template rule "If the same test fails three times, stop and report", allows the stop with `{"systemMessage": "NOT DONE: gate still red after 3 attempts (<last failure kind>, tree <tree>); this session ended without a passing gate"}`. The last-red state from that run is already recorded (step 8). After attempt 3 the counter resets to 0, so the next stop in the same session gets two more blocks before another NOT DONE. A pass deletes the session file, and session files older than 7 days are pruned on each run. Every path out of a red gate is either a block or a visible NOT DONE, never a silent stop.
   - **Budget.** `--budget` (adopt writes it) is the hook's `timeout` minus 30s. Gate enforces one deadline (start + budget) across the slot wait and the run. When the deadline is reached, gate kills the process group and blocks (`decision: block`, counted toward the loop guard) with `gate: timed out (waited Ns for a slot, ran Ns)` in both the reason and a `systemMessage`, so Claude Code never kills the hook itself. That would be a non-blocking error, and the stop would go through.
   - Go parses the stdin JSON, so a missing `jq` no longer matters.
10. **`--status [<rev>]`** is read-only and never runs the command. For `<rev>` (default: the current working tree) it looks up `<rev>^{tree}` and prints the PASS receipt (age, command, duration) or `unproven` / `unproven (last attempt RED: <kind>)`. It also reports integrity problems, with a check for each case:
    - **Receipt vs. config:** `config drift` if the receipt's `config_hash` doesn't match the current `gate` object.
    - **`.newproj.json`:** `uncommitted config` if it isn't committed. `config drift` if it's committed and differs from the merge base with the default branch (origin/HEAD → init.defaultBranch → main).
    - **Hook entry (D2, D15):** read the main checkout's `.claude/settings.local.json` (via `git rev-parse --path-format=absolute --git-common-dir`) or the committed `.claude/settings.json`; print `hook missing` when no entry satisfies `gate.IsGateHook`, and warn when a local entry's absolute binary path no longer exists.

    This is how a human sees which branch is actually proven, and whether the setup that proved it has been tampered with.

### `newproj adopt`

```
newproj adopt [--apply] [--cmd "<command>"] [--agents-file AGENTS.md|CLAUDE.md] [--shared] [--hook-timeout 1800 (min 60)]
```

1. **Detect** candidate verify commands, ranked:
   - Makefile targets: `check`, `ci`, `verify`, `test`, `lint`.
   - justfile recipes with the same names.
   - package.json scripts: `check`, `test`, `lint`, `typecheck`, composed with `&&`.
   - Cargo: `cargo clippy -- -D warnings && cargo test`.
   - go.mod: `go vet ./... && go test ./...`.

   Flag names that usually mutate (`fmt`, `format`, `fix`) and suggest their check forms. `--cmd` overrides detection.
2. **Plan, dry run by default:** print the chosen command, the other candidates, and a unified diff of every file it would write:
   - `.newproj.json`;
   - a Stop hook entry merged in, leaving existing hooks in place, with an explicit `"timeout": <--hook-timeout>` (default 1800s) and the command from `gate.HookCommand` (D6): the absolute `os.Executable()` path for the local target, a PATH lookup for `--shared` (D15). For `--shared`, the entry is inserted with a minimal text patch that preserves formatting (D17). **Target file:** `.claude/settings.local.json` by default, so teammates who pull the repo never inherit the hook; `--shared` writes `.claude/settings.json` instead. **The command is identical for both targets** and handles a missing binary the same way:
     `command -v newproj >/dev/null 2>&1 || { printf '{"systemMessage":"done-gate NOT enforced: newproj is not on PATH"}\n'; exit 0; }; newproj gate --hook --budget <timeout-30>s`
     A missing binary therefore **fails open, visibly**. The stop goes through, and the user sees the message through `systemMessage`, the channel Claude Code shows on exit 0. It isn't fail-closed: blocking would trap an agent in a stop loop that no counter can bound, because the counter lives in the missing binary. The design states this plainly rather than claiming otherwise. The dry-run diff names the target file;
   - **Ignore guarantee for the local target.** If `git check-ignore -q .claude/settings.local.json` fails, adopt appends `.claude/settings.local.json` to `.git/info/exclude`, the per-clone ignore file that changes no tracked file, so an agent's `git add -A` can't commit the hook. The plan lists this as a step;
   - a marked block (`<!-- newproj:begin --> … <!-- newproj:end -->`) appended to CLAUDE.md if it exists, else AGENTS.md if it exists, else a new CLAUDE.md (D10). The block covers the definition of done, worktree-per-task, and bd rules only when bd is on PATH.
3. **`--apply`:** write those files idempotently (re-running replaces the marked block and hook entry, never duplicates them). Then run `newproj gate` once and print `READY` only on pass. On fail, print `NOT READY: gate is red` with the output. The files stay written, so the user can fix the gate.
4. Never moves the repo, never commits, never touches CI files in v1. The dry run lists every side effect: `refs/notes/newproj-gate`, the session/last-red state dirs and the `.git/info/exclude` append (D10).
5. **Linked worktrees, which is where parallel agents run (D2, D12).** Claude Code uses the main checkout's `.claude/settings.local.json` in a worktree (per its settings docs; proven by the step-0 probe before gate code). The config still has to reach worktrees: `--apply` ends with `READY — commit .newproj.json so new worktrees inherit the gate`, and `--status` reports `uncommitted config` until it is. If the probe shows worktrees do not read the main checkout's local settings, `--shared` becomes adopt's default.

## Open Questions

1. **Receipts off-machine.** Notes on tree objects don't push by default. Approach B's CI verification needs either `git push origin refs/notes/newproj-gate` or a commit trailer. Defer, but keep the JSON format stable.
2. **Slot default.** CPUs/4 is a guess. Measure with four agents on a real Go repo.
3. **Mutation guard false positives.** Tools that write tracked caches or lockfiles (e.g. `npm install` updating package-lock.json) will trip it. Guard intentionally, and document it as "your check must not write tracked files".
4. **Multiple detection candidates.** In v1, pick the top-ranked one, show the rest, and let `--cmd` override. No interactive prompt, so it stays scriptable.
5. **`--container` and `wt`.** Port `repo-adopt` and `wt-*` after v1 as thin layers. `wt done` calls `newproj gate` and refuses without a receipt.
6. **Naming.** "newproj" undersells a tool whose product is the gate. Decide before the first public release.

## Success Criteria

- `newproj adopt` (dry run) on three public repos you don't own (one Go, one TypeScript, one Rust) proposes a sensible verify command with zero file changes.
- `newproj gate` exits non-zero in each of: no `.newproj.json`, command not on PATH, command fails, command modifies the tree. Each case has a test. A file edited while gate waits for a slot does **not** trip the guard (baseline taken after the lock).
- Tree-hash tests: a tracked-but-ignored file's change changes the hash; the hash is identical from the main checkout and a linked worktree at the same state.
- Four concurrent `newproj gate` runs with `NEWPROJ_SLOTS=2` never have more than two commands running at once, even when they come from two different repos (test with a sleep-and-record command).
- Four worktrees of one repo pass concurrently and all four receipts exist afterwards (ref-lock retry test).
- A second `gate` on an unchanged tree returns a cached pass in under 1s on a repo with at least 10k tracked files.
- In Claude Code, an agent in an adopted repo can't end a session on a red gate silently: stop attempts 1-2 are blocked, and attempt 3 ends with a red receipt and a `NOT DONE` message (manual hook test, recorded for the README).
- A check that sleeps past `--budget` makes gate exit 4 with `gate: timed out` before the hook's `timeout` fires (test with a short budget). A check that *always* times out still ends at attempt 3 with the NOT DONE `systemMessage` (counter test).
- Manual hook tests, recorded: the attempt-3 NOT DONE message and the missing-binary message both appear in the Claude Code UI.
- `adopt --apply` in a repo that doesn't ignore `.claude/settings.local.json` leaves `git status` clean of that file (entry added to `.git/info/exclude`).
- After the hook entry is deleted from `.claude/settings.local.json`, `gate --status` prints `hook missing`.
- In a linked worktree created after adopt plus a commit of `.newproj.json`, the main checkout's hook fires for a Claude session in the worktree and gate checks the worktree's own tree (D2, D7); a missing `.newproj.json` still ends at attempt 3 with NOT DONE rather than blocking forever.
- A SIGKILLed gate leaves its slot held until the check's process group exits; a check with a sleeping grandchild leaves no process behind after a timeout (D5, D13).
- `newproj gate --status` prints `PASS`, `unproven` or `unproven (last attempt RED: <kind>)` for the working tree and for a given rev without running the command, and prints `config drift` after `.newproj.json` is edited on a branch.
- `newproj new demo && cd demo/main && make check` passes, and `make check` leaves `git status` clean.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: MAX_ITERATIONS

### R3-1 — feasibility (blocking)

**Problem**

> The loop guard resets the counter whenever the step 5 baseline tree changes. A check that writes tracked files leaves the worktree mutated, so the next attempt's baseline is the mutated tree and the counter resets. For any non-idempotent writer (timestamps, generated files, lockfile churn) the baseline differs on every attempt, the counter never reaches 3, and the agent is blocked indefinitely. This contradicts the claim that a check which keeps rewriting the tree still counts, and the claim that runaway loops are bounded.

**Remedy**

> Don't reset the counter on tree changes the gate itself caused. For example, record the post-run tree of a guard failure and reset only when the next baseline differs from that post-run tree, or count consecutive red outcomes per session regardless of tree. Add a counter test with a check that writes a timestamp to a tracked file.

### R3-2 — completeness (blocking)

**Problem**

> Step 1 exits 2 when there is no config, the command is empty, or the command isn't found. In hook mode, exit 2 blocks the stop, but the counter's list of blocking outcomes leaves out these step 1 cases. A hooked worktree with no `.newproj.toml` (likely, because adopt leaves it uncommitted and linked worktrees don't get untracked files) or with a missing tool blocks every stop forever and never reaches the attempt-3 NOT DONE exit. That contradicts 'Every path out of a red gate is either a block or a visible NOT DONE'.

**Remedy**

> Count the step 1 failures (no config, empty command, command not found) in the session counter, keyed to the pre-lock tree, so they also end at attempt 3 with a NOT DONE `systemMessage`. Add a counter test for a hooked worktree with no `.newproj.toml`.

### R3-3 — feasibility (blocking)

**Problem**

> The default hook target, `.claude/settings.local.json`, is gitignored, and adopt leaves `.newproj.toml` uncommitted. Linked worktrees created with `git worktree add` (the parallel-agent case the product is for, with worktrees in `<repo>.wt/`) contain neither file, so agents in those worktrees run with no Stop hook at all unless the worktree tool happens to copy them. The `--status` hook check stores one record per repo (keyed by the git common dir) while the target file is per worktree, so it will report `hook missing` in every linked worktree without saying how to fix it. The headline demo ('four agents can't accidentally claim done') isn't delivered under the default setup.

**Remedy**

> State how linked worktrees get the hook and the config. Options: recommend committing `.newproj.toml` and say so in adopt's output; have gate find the config through `git rev-parse --git-common-dir` as a fallback; provide a step (or document the gtr/agent-worktree copy-file setting) that installs the local hook into each new worktree; or make `--shared` the recommended mode for parallel agents. Make `--status` per-worktree aware and add a success criterion for a hooked linked worktree.

### R3-4 — consistency (blocking)

**Problem**

> Every outcome now writes a receipt with `git notes add -f` keyed to a tree. A timeout during the slot wait writes a RED receipt for a tree that was never tested, which contradicts step 8's own 'every run that reaches the command' rule. Because `-f` overwrites, that RED (or a guard failure caused by a concurrent edit) can replace a PASS that another worktree at the same tree just recorded. Two worktrees at the same commit are common. `--status` would then show RED for a tree that actually passed, undermining 'how a human sees which branch is actually proven'.

**Remedy**

> Define receipt precedence. For example, never overwrite an existing `exit=0` receipt with a non-verdict outcome (slot-wait timeout, guard failure). Either don't write receipts for slot-wait timeouts (track them only in the session counter), or record them as a distinct non-RED status. Alternatively, append per-run entries and have `--status` define which one wins. Align step 8's 'reaches the command' wording with that rule.

### R3-5 — consistency (blocking)

**Problem**

> Hook mode blocks with exit 2 and stderr, and Claude Code ignores stdout JSON on exit 2. A receipt-write warning raised on a blocked attempt (attempts 1-2, or any exit-2 path) therefore can't go out as a `systemMessage` as promised. Step 8 also says the warning 'is added to its message', which on exit 2 reaches only the agent. The two rules contradict each other on the block path.

**Remedy**

> State the channel for warnings on the block path: either append them to the exit-2 stderr (agent-visible only) and say so, or block with exit 0 plus JSON `{"decision":"block","reason":...,"systemMessage":...}`, which Claude Code supports for Stop hooks and which shows the warning to both the agent and the user.

### R3-6 — clarity (minor)

**Problem**

> The design doesn't say what happens to the counter after attempt 3 allows the stop. If the user prompts again in the same session and the agent stops on the same red tree, attempt 4 could block again, allow again, or start over.

**Remedy**

> State that the NOT DONE exit resets the counter (or that it keeps allowing with NOT DONE), and say which.

### R3-7 — consistency (minor)

**Problem**

> Unchanged text is now stale. The pitch calls the gate 'fail-closed' while the missing-binary path deliberately fails open, and the guarantee section says `gate --status` flags hook drift 'from the base branch' while step 10 now detects hook changes through local adopt state.

**Remedy**

> Qualify 'fail-closed' as applying once newproj is installed and the config is present, and update the guarantee paragraph to match step 10's per-target checks.

### R3-8 — clarity (minor)

**Problem**
